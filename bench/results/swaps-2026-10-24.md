# Keyed row swaps

The block renderer now uses native atomic moves for existing nodes within
the same parent. The change is in `__htmsIns`; it applies to keyed reorders
and multi-node blocks without changing the reconciliation algorithm.
New nodes and browsers without the API still use `insertBefore`.

The measured improvement is in scripting and style work. A mirrored
confirmation run reduced swap scripting medians by 12–17%. Its pooled
click-to-paint median was 1.6% lower, but the latency interval includes
zero. The full run also had a faster unchanged control, so these results
do not establish a repeatable end-to-end swap win.

## Final measurements

The full run used the unchanged runner with 15 samples per operation,
interleaving all five frameworks, vanilla JS and the retained HTMS build.
Raw samples and environment details are in [results.json](results.json).
The compiler revision is `97be75f`; the retained build is `e0dc8e8`.

| Full run | Before | After | Solid |
| :-- | --: | --: | --: |
| Swap, click to paint | 20.746 ms | 22.859 ms | 23.232 ms |
| Swap, scripting | 0.498 ms | 0.483 ms | 1.528 ms |
| Overall geometric mean vs vanilla | 1.0202× | 1.0402× | 1.0848× |

The new build finished ahead of Solid in this run, while the unchanged
HTMS control finished ahead of both. This table is retained as measured;
the subsequent confirmation does not replace it in the framework charts.

### Mirrored confirmation

The follow-up fixed the app order as `after, before, Solid, before-copy,
after-copy` for 51 rounds. The copies are byte-identical built bundles.
This gives each HTMS revision 102 samples across mirrored positions and
Solid 51 samples, using the same fresh pages, warm-ups, real clicks,
CPU slowdown and trace boundaries as the full run. No runner changes were
needed. Raw results are in [swaps-confirmation.json](swaps-confirmation.json).

| Confirmation | Before | After | Solid |
| :-- | --: | --: | --: |
| Pooled click-to-paint median | 21.181 ms | 20.837 ms | 21.971 ms |
| First copy: scripting median | 0.518 ms | 0.455 ms | 1.411 ms |
| Mirrored copy: scripting median | 0.625 ms | 0.518 ms | — |

For each round, averaging the two after samples and subtracting the
average of the two before samples gives a mean difference of −0.390 ms.
The approximate paired 95% t interval is −0.894 to +0.115 ms (51 rounds).
That does not establish a latency improvement. The lower scripting
medians and reduced style count support keeping the small helper change;
most of the browser's frame work remains.

The separate warmed check, `node bench/rows.mjs htms-base,htms,solid 1000`,
measured swap scripting at 0.120 ms before and 0.105 ms after, with Solid
at 1.170 ms. Its nine rotating samples are in
[swap-scripting.json](swap-scripting.json). Those script-only times use
a different warm-up and measurement window from the traced benchmark.

## Why Solid's lead needed a closer look

The first 15-sample swap run reproduced the previous report's ordering:
HTMS took 26.700 ms and Solid 25.968 ms from click to paint. HTMS's script
time was already lower, at 0.687 ms versus Solid's 1.543 ms.

That small total-time lead did not hold consistently. A later 31-sample
run put the unchanged HTMS build at 21.152 ms and Solid at 22.183 ms.
These comparisons use the same `e0dc8e8` HTMS build. Browser rendering and
frame variation dominate the result, so an isolated win here does not
establish that one framework has a faster swap implementation.

The apps produce the same table structure. HTMS has one additional custom
element host outside the table. Both make two DOM moves, though Solid
inserts the trailing row immediately after the leading row on the first
move, while HTMS inserts it before the leading row. Trying Solid's move
order did not improve HTMS's total time reliably.

Exploratory measurements, including all samples, are in
[swap-investigation.json](swap-investigation.json). Its variant names
describe temporary compiled runtime changes, not benchmark app changes.

## The change

`insertBefore` removes and reinserts an existing node. Where available,
[`moveBefore`](https://developer.mozilla.org/en-US/docs/Web/API/Element/moveBefore)
moves it without resetting its rendering state. The helper uses it only
when the node is already a child of the target parent. That also satisfies
the API's same-document and matching connected-state requirements.

This avoids some browser work when moving the rows. It also preserves
focus and allows custom elements with `connectedMoveCallback` to handle
the move without disconnecting and reconnecting. It does not eliminate
the table's sibling-selector restyling or its layout and paint work.

The first saved swap frames in the final run restyled 1,017 elements for
the retained build and Solid, versus 1,001 for the native move path.
The HTMS layout tree still contained 12,066 objects in both cases.
[swap-profile.json](swap-profile.json) records those counts and frame
timings. These are single illustrative traces, not median phase timings.
Reconciliation still scans the list; this change reduces the work of
moving its nodes.

The benchmark bundle grew from 4,729 to 4,747 bytes with gzip (+18 bytes).
The implementation adds no persistent data structures.

## Other experiments

Changing DOM move order, reusing the block array for a verified two-item
exchange, and using `replaceChild` for single-node exchanges all failed to
repeat their initial total-time gains. They were discarded. The retained
change uses the existing general move helper; it has no benchmark-specific
index, row count or swap pattern.

## Verification

All 364 Jest tests, 26 browser tests, lint, TypeScript checks, the production
build and Vite integration passed. The four new browser cases cover native
moves and an explicitly disabled API, for both single-node and multi-node
rows. They check node identity, index bindings, sibling anchors, later
insertions/removals, unfinished input values and custom-element callbacks.
Native moves also retain focus in these checks.

Chromium 141 resets an input's selection range during a native move. This
was reproduced with plain DOM calls outside HTMS. The browser checks do
not promise caret preservation; the component documentation now qualifies
the earlier broad focus/selection guarantee.

The benchmark apps, CSS, build script, runner and operation definitions
are unchanged. The final comparison retains the `e0dc8e8` bundle as
`htms-base` and measures it alongside the current build in the same run.
The full run completed 945 operation samples, 105 startup samples and
21 heap passes; the mirrored confirmation added 255 operation samples.
